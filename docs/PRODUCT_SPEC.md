# 事件证据工作台：20 小时交付版 PRD

## 1. 产品定位

**一句话**：把同一投资事件的多份材料拆成可核查的主张，保留证据和版本，让研究员快速回答“目前知道什么、为什么这样判断、与我关注的公司有什么关系”。

**目标用户**：每日跟踪自选股的个人投资者或初级研究员。典型任务是看到一则新闻后，在 2–3 分钟内确认是否为旧事件的新进展、消息源头在哪里、哪些说法获得确认或遭否认，随后决定是否继续人工研究。产品不给买卖建议。

**MVP 范围**：一个可追溯的真实主事件，5–8 份材料；一件与主事件相似但不同的事件，用于验证误合并；1–2 条明确标注为**模拟测试材料**的更正、否认或过期材料。用户能从浏览事件走到导入新材料、确认事件归属、看到结论与通知变化。公开文本接口不可用时，允许手工录入来源 URL、引文与时间；界面如实标注“手工录入”。

## 2. 用户操作路径与三处核心界面

| 步骤 / 界面 | 用户做什么 | 界面必须展示 / 产出 |
| --- | --- | --- |
| 1. 事件列表 | 选关注标的，找到有新变化的事件 | 事件标题、直接涉及的标的、当前结论摘要、最后一次**披露**时间、未读变化标记；点击进入详情。列表不把抓取时间写成事件发生时间。 |
| 2. 事件详情 | 看事件源头、时间线、逐项主张，检查原文 | 顶部“当前能确认什么”及依据时间；主张卡同时展示**表述类型**与**核验状态**；支持/反驳/更正证据及原文片段、URL、来源关系；按披露时间排列的版本时间线；四种时间可展开查看；直接/间接关联标的分列。 |
| 3. 导入与核对抽屉 | 粘贴原文或链接，补充来源、时间，核对 AI 建议，确认提交 | AI 提取的主体、动作、对象、金额/项目等事件锚点；“建议合并到事件 A / 新建事件”的理由及不确定项；待入库的原子主张与引文；用户可修改、拒绝合并或新建。确认后返回详情，显示前后变化与站内通知。 |

**关键文案示例**：

- “已披露合作意向；正式订单金额仍待核实。”
- “这篇报道转述同一公告，不计作新增独立证据。”
- “新公告否认了‘已签正式合同’，结论由‘待核实’更新为‘被否认’。查看原文。”
- “发生时间未披露；以下按公开披露时间排序。”
- “材料已过其适用日期，结论需复核；过期不表示原说法为假。”

## 3. 最小信息模型

| 对象 | 必需字段 / 关系 | 约束 |
| --- | --- | --- |
| 来源 `Source` | 标题、发布机构、来源类型、原文 URL、原文/片段、来源链或被转载源；`occurred_at`、`disclosed_at`、`ingested_at`、`updated_at` | 四种时间分别保存，未知为 `null`；抓取时间由系统记录；同一 URL 或相同正文可提示重复。原文修改生成来源新版本，不能覆盖。 |
| 事件 `Event` | 主体、事件动作、对象/项目、事件类型、直接关联标的、间接关联说明、当前摘要 | “同一公司”不是合并充分条件；主体+动作+对象/项目+时间窗口共同构成候选键。当前摘要来自主张状态，不代替证据。 |
| 主张 `Claim` | 可单独核验的一句话、结构化主体/谓词/对象、表述类型、核验状态、引文位置、有效截至时间（若有） | 一句话只表达一个可核验命题。**事实陈述**表示作者以事实语气陈述，不表示已证实。 |
| 证据关联 `EvidenceLink` | 来源版本、主张、关系（支持/反驳/更正/仅提及）、精确引文、是否原始或转载 | 多篇转载同一出处只算一个证据源；只引用标题不足以支持正文中的数字。 |
| 版本 `Revision` | 事件、变更时间、旧/新主张状态、变更原因、触发来源 | 追加写入；能回看某一披露时点“当时公开可知什么”。 |
| 通知 `Notice` | 关注标的、关联事件、旧/新结论、证据 URL、触发类型、已读状态 | 关键主张的确认、否认、更正、到期复核才通知；普通转载不重复通知。 |

**两个维度必须分开**：主张的表述类型是“事实陈述 / 观点 / 推测 / 传闻”；核验状态是“已确认 / 待核实 / 存在冲突 / 被否认 / 已更正 / 到期需复核”。例如新闻以肯定语气写下的订单金额仍可能是“事实陈述 + 待核实”。

**时间语义**：`occurred_at` 是事件在现实中的发生时间，`disclosed_at` 是来源首次公开的时间，`ingested_at` 是系统收录时间，`updated_at` 是来源内容修改时间。按“当时已知”检索时，仅使用截至该时点已公开的来源版本；不能把之后公告揭示的发生时间倒灌为当时已知信息。无披露时间时显示未知并按抓取时间暂排，明确提示排序依据。过期仅在材料给出适用截止日或人工设置复核日后触发。

## 4. AI、规则与人工的分工

| 任务 | 执行者 | 失败时的处理 |
| --- | --- | --- |
| 提取实体、事件锚点、原子主张和对应引文；提出同事件候选；解释新旧说法差异 | AI | 输出必须带来源片段；无法引用的内容标为“未抽取到证据”，不能生成确定结论。 |
| URL / 文本重复检测、四类时间字段校验、转载源去重、保存不可覆盖的版本、依据已确认关联触发通知 | 程序规则 | 接口失败或时间缺失时保留原材料，提示待人工补录/复核；不编造字段。 |
| 确认模糊的事件合并、修改抽取错误、判定证据是否足以改变关键主张、处理来源冲突 | 用户 | AI 建议在确认前是草稿；必须允许拒绝候选并新建事件。 |

**证据权重展示**采用可解释标签（原始公告 / 一手采访 / 二手转述 / 匿名传闻、是否独立、是否被后续更正），不输出未经校准的“可信度 93%”。公司公告对其合同披露具有较强直接性，但仅能支持其实际披露的命题；“签意向书”不能证明“收入已确认”。研报对未来的判断标为观点/推测，即便引用了真实公告也不升级为已发生事实。

## 5. 版本迁移与通知

| 新材料 | 当前结论如何变化 | 通知内容 |
| --- | --- | --- |
| 独立一手材料确认原主张 | 待核实 → 已确认 | 告知确认了哪一项、披露时间与原文。 |
| 来源补充新细节，但不推翻原结论 | 新增主张或细化已知范围；旧版本保留 | 仅关键细节变化通知。 |
| 权威来源明确否认具体主张 | 待核实/冲突 → 被否认；其他未涉及主张不变 | 明示被否认的**具体说法**，不能写成整个事件不存在。 |
| 原来源发布更正 | 原主张 → 已更正；新主张另建并核验 | 展示“原说法 → 新说法”和更正来源。 |
| 有效日期已过且无新资料 | 到期需复核；不自动判为假 | 提醒复核，不给真假结论。 |

有争议时先显示“存在冲突”，列出双方主张及来源，不让模型用流畅摘要抹平矛盾。关联标的仅展示“直接披露主体 / 间接关联及理由”，不据此推断股价因果或投资收益。

## 6. 20 小时验收标准

1. 评委打开公开 URL，无需读代码即可从事件列表进入详情，看到源头、当前主张、版本时间线，并点开每项关键结论的原文 URL 或明确的模拟标识。
2. 评委输入一份新材料，系统返回至少两个事件归属选项或“新建”，说明推荐理由；评委可改选并确认。确认后时间线、受影响主张及站内通知随之变化。若 API 不可用，手工录入链路仍能运行。
3. 主事件中至少展示一次“待核实 → 已确认 / 被否认 / 已更正”的可回放变化；同公司不同事件不能仅因公司相同被合并；重复转载不增加独立证据数。
4. 所有展示的关键数字和结论有明确来源、引文和披露日期。四种时间可分别检查，未知字段不得用抓取时间冒充。
5. 至少检查：误合并、重复转载、事实与观点误判、相互冲突、原文/接口缺失、缺失时间、更正、到期复核、投资建议越界。记录实际结果及未通过项，不把未测试的指标写成已达成。

**交付顺序**：先建可追溯材料包和主张标准答案，再完成三界面闭环，最后录制 60–180 秒演示视频并补 README、AI 使用与验证记录和测试说明。可选的股价影响图、外部实时爬取、多账户协作、自动推送留在“未做事项”；它们不影响这条主链路是否成立。
